调试过程中的问题
一、数据层（data-structures.js）
问题1：排序链表插入时的中文排序失效
按姓名排序的单链表最初使用 JavaScript 默认的字符串比较运算符（> / <），但中文字符的比较基于 Unicode 码点而非拼音顺序。例如"张"的 Unicode 码点为 U+5F20，"陈"的码点为 U+9648，导致"张伟"排在"陈明"前面，这与拼音顺序（C在前Z在后）完全相反。此外，JavaScript 的 > / < 对中文字符的比较行为在不同浏览器中不完全一致，Chrome 和 Safari 可能给出不同的排序结果。解决方法：将比较逻辑改为 name.localeCompare(otherName, 'zh')，指定中文 locale（zh 代表中文）进行拼音排序。localeCompare 返回 -1、0 或 1，分别表示小于、等于和大于，正好对应排序所需的比较语义。插入逻辑的完整边界条件包括三类：空表插入时 head 为 null，直接将新节点设为 head；表头插入时新节点 name 小于 head.name，需要将新节点插在 head 之前并更新 head 指针；表中间/表尾插入时，遍历找到第一个 name 大于新节点的位置，将新节点插入其前。遍历条件 while (cur.next && cur.next.name.localeCompare(name, 'zh') <= 0) 中的 <= 保证同名人插入时按先后顺序排列（后插入者排在后面），同时 cur.next 的 null 检查防止在表尾时访问 null 的属性导致 TypeError。调试过程中发现一个容易遗漏的细节：如果 while 条件写成 cur.next.name.localeCompare(name, 'zh') < 0（严格小于），同名人会插入到已有同名者之前，虽不影响正确性但改变了"后到者排在后面"的直觉行为。此外，当链表中存在英文名和中文名混合时，localeCompare 能将英文名正确排在中文名之前（拉丁字母在拼音排序中优先级高于 CJK 字符），符合实际业务中多语言旅客名单的需求。
问题2：链式队列 enqueue() 指针不同步
enqueue() 方法在队列非空时执行两步操作：先将新节点链到队尾（this.rear.next = node），再将 rear 指针移动到新节点（this.rear = node）。如果在编码时只写了第一步而遗漏第二步，rear 指针将永远停留在第一个入队的节点上。后续每次 enqueue 都会覆盖 rear.next，导致之前入队的节点因为没有任何引用而被垃圾回收，队列中永远只保留最后一个入队的节点。这是链式队列实现中最经典的 bug：front 和 rear 双指针的一致性维护。最初遇到这个 bug 时的表现是：在 Console 中连续执行 enqueue('张三', 1, 3)、enqueue('李四', 2, 2)、enqueue('王五', 1, 1) 三个操作后，调用 toArray() 发现只返回了'王五'一条记录。排查过程：首先在 toArray() 中增加 console.log 打印遍历路径，发现链表只有一个节点。然后在 enqueue() 内部对每次调用前后分别 console.log front 和 rear 指针的指向以及 rear.next 的值，发现 rear 始终指向第一个入队的节点，其 next 被反复覆盖。定位到遗漏 this.rear = node 语句后修复。这个 bug 的隐蔽之处在于：如果只入队一次就出队，rear 指针刚好正确（只有一个节点时 front === rear），只有连续入队两次以上才会暴露。这也说明测试时仅覆盖"入队一次+出队一次"的简单场景是不够的，需要覆盖连续入队、连续出队、交替入队出队等更复杂的操作序列。另一个相关注意点是空队列的入队：当 rear 为 null 时，需要将 front 和 rear 同时指向新节点（this.front = this.rear = node），创建队列的第一个节点，而不是走 rear.next = node 的分支。
问题3：dequeue() 队列变空的边界处理
dequeue() 执行后 this.front 移动到原队头的下一个节点。如果移除了队列中唯一的节点，this.front 变为 null，此时必须同步将 this.rear 也设为 null。如果 rear 没有同步清空，它会继续持有对被移除节点的引用，形成"幽灵引用"。当后续再次 enqueue 时，代码检测到 rear 不为 null，就会走 rear.next = node 的分支——但此时 rear 指向的是一个已经从队列中移除的孤立节点，将新节点链到它后面会导致新链表悬挂在一个无主节点上，而 front 仍然为 null，最终队列的 front 和 rear 指向不同的链，整个队列结构完全错乱。这个问题的排查思路：在 dequeue 操作后立即检查 if (!this.front) this.rear = null。此外还需要警惕的是，JavaScript 的垃圾回收机制虽然会自动回收不可达对象，但如果 rear 持有对被移除节点的引用，该节点就不会被回收——虽然是单节点泄漏，但在频繁 enqueue/dequeue 的长时间运行中（如一天的航班订票操作）会逐步积累。正确的 dequeue 实现是：先保存 this.front 引用；将 this.front 移到 this.front.next；如果 this.front 变为 null，将 this.rear 也设为 null；this._size 减 1；返回保存的节点引用。每步顺序不可颠倒——如果先 size-- 再保存引用，在某些异步场景下可能出问题。
问题4：removeByName() 移除队尾元素的 rear 更新
removeByName() 通过遍历链式队列找到目标节点并将其从链表中剔除，操作模式是 cur.next = cur.next.next。当被删除节点恰好是队列的最后一个元素（rear 节点）时，cur.next.next 为 null，cur.next 被设为 null 后 cur 成为新的队尾，但 rear 指针仍然指向已被移除的旧节点。这导致后续 enqueue 操作将新节点链到已移除的 rear 节点后面，而新节点实际上成了孤立链的一部分，front 仍然指向原队列头，队列状态分裂。解决方法：在 cur.next = cur.next.next 之后增加 if (!cur.next) this.rear = cur，即如果当前节点之后没有节点了，说明当前节点已成为新的队尾，需要更新 rear 指针。与之对称的边界情况是删除队头元素：如果 cur.next 是队头（cur 为虚构头节点的情况不适用），实际上 removeByName 中如果要删除的是队头，会走 this.front.name === name 分支直接调用 dequeue()，此时 dequeue() 已经处理了 front 和 rear 的同步问题。
问题5：toArray() 遍历的性能与状态一致性
toArray() 方法遍历整个链表/队列并将节点数据展平为纯对象数组。这个方法在多个关键路径上被频繁调用：_persist() 序列化、occupiedSeats() 构建已占用座位集合、UI 层渲染已订票列表和候补列表。每次调用都是 O(n) 的完整遍历，且返回的数组是链表数据的"快照"——如果在遍历过程中链表被修改（如在 UI 渲染回调中触发了新的退票操作），快照可能不完整或出现数据不一致。本系统中由于 JavaScript 单线程特性，在同步代码执行期间不会出现真正的并发修改，但异步回调（如事件处理）中的修改仍需注意。toArray 的设计选择是返回纯数据对象而非暴露节点引用，好处是隔离了内部数据结构（外部无法通过返回对象修改链表），代价是每次都需要创建新对象，在大型数据集（如包含 500 个已订票客户的链表）上会产生一定的 GC 压力。
二、业务层（airline-system.js）
问题1：候补队列补位策略的公平性缺陷
退票触发的 _fulfillWaitlist() 最初的设计逻辑是：遍历整个候补队列，对每个候补者，如果余票足够就分配，不够就跳过继续看下一个。例如：某航班退票释放 2 张余票，候补队列从前到后依次是[刘鹏飞(需3张)、陈雨桐(需1张)、赵明轩(需2张)]。按原逻辑，刘鹏飞需要 3 张但只有 2 张余票→跳过；陈雨桐只需 1 张→余票够→分配给陈雨桐；剩余 1 张→赵明轩需要 2 张→不够→跳过。结果是陈雨桐（排在第 2 位）拿到了票，而刘鹏飞（排在第 1 位）被跳过。这严重违反了链式队列 FIFO（先进先出）的核心语义——排在前面的人因为需求量大反而被永久跳过，而且随着后续退票释放更多余票，刘鹏飞之前的跳过无法自动恢复（除非手动再次遍历整个队列）。真正的 FIFO 队列要求队头优先得到服务，即使队头暂时无法满足，也不应该跳过它去服务后面的人。解决方法：改为"全有或全无"策略——在 while 循环中只检查 peek() 返回的队头元素，如果 front.ticketCount <= remaining，则 dequeue 该队头并为其分配座位，继续检查新的队头；如果 front.ticketCount > remaining，直接 break 跳出循环，保留队头及其后的所有候补者等待下一轮退票释放更多余票。这个策略在公平性和实现简洁性之间取得了平衡。但需要注意一个极限场景：如果队头需要 10 张票而航班每次退票只释放 1-2 张，队头可能永远等不到一起满足的机会。真实航司系统对此的改进是支持"分票"——将大需求拆分为多次部分满足，但实现复杂度显著增加。这个策略选择过程的收获是：数据结构的选择不仅决定了操作的复杂度，也隐含了业务策略的约束——链式队列的名字本身就在暗示 FIFO 公平性，任何破坏这一原则的实现都需要有充分的理由。
问题2：generateSeatNumbers() 跨舱位回退时的重复分配
座位分配采用两轮策略。第一轮在目标舱位范围内按行列顺序遍历分配：头等舱（第 1-2 排，A/C/D/F 四列）、商务舱（第 3-5 排，A/C/D/F 四列）、经济舱（第 6+ 排，A-F 六列）。如果目标舱位座位不足，第二轮从整个飞机的全局空座中补充（包含头等舱和商务舱的剩余空位），实现"跨舱位回退"。最初两轮之间未排除第一轮已分配的座位号，导致 seats 数组中出现重复的座位 ID。同时，两轮循环都需要通过 occupiedSeats() 获取已被现有订票客户占用的座位集合并在分配时排除，但第一轮中已分配的座位尚未写入 bookedList（此时只是生成座位号列表，尚未正式订票），occupiedSeats() 无法感知这些"即将分配但尚未持久化"的座位。这就形成了三组需要排除的座位：已被现有订票记录的（通过 occupiedSeats 获取）、已被第一轮分配的（通过 seats.includes 检查）、以及超出飞机容量范围的（通过 globalIdx <= capacity 检查）。修复后的两轮逻辑：第一轮在目标舱位行列内查找，条件包括 not in occupiedSet and not in seats and globalIdx <= capacity；第二轮在全局行列内查找，条件包括 not in occupiedSet and not in seats（通过第一轮已装入 seats 数组来排除）and globalIdx <= capacity。经过这样的三重过滤，确保不会出现重复分配。
问题3：occupiedSeats() 的重复计算与性能浪费
occupiedSeats() 方法的工作原理是通过 bookedList.toArray() 遍历链表获取所有订票记录，然后对每条记录的 seatNumbers 数组进行迭代，将每个座位号加入一个新建的 Set 对象并返回。在 _persist() 和 load() 之外，这个 Set 不会被缓存。在以下场景中会反复调用：generateSeatNumbers() 内部调用一次；bookTicket() 在验证手动选座时调用一次（检查自定义座位是否已被占用）；getSeatMap() 在渲染座位图时为每个座位的 occupied 属性调用一次；每次 UI 刷新座位图时也间接触发。在最极端的情况下——满员航班（280 人已订票）渲染座位图——需要遍历整个 280 节点的链表，提取全部座位号构建 Set，然后对 300 个座位逐一判断是否在 Set 中。虽然单次操作在毫秒级，但如果用户在订票页面频繁切换航班（每次切换触发 renderSeatMap），多个 O(n) 操作叠加会造成可感知的延迟。解决方法是：在 generateSeatNumbers() 中将 occupiedSeats() 的调用提到循环外，将结果存入局部变量；在 getSeatMap() 中也只调用一次存入局部变量后复用。更根本的优化方案见"算法改进设想"第 3 条。
问题4：跨日航班飞行时长的计算
calcDuration() 函数将起飞和到达时刻（格式 "HH:MM"）分别解析为小时和分钟，转换为当日分钟数后相减。对于大部分航班（同日到达），直接相减即可得到正确的飞行时长。但国际长途航班（如北京→悉尼 CA175，15:00 起飞、次日 08:30 到达）和红眼航班（晚间起飞、次日凌晨到达）中，到达时刻的分钟数小于起飞时刻的分钟数，直接相减得到负值。最初实现没有考虑这种情况，导致 CA175 的 duration 显示为负值（8:30 - 15:00 = -390 分钟），UI 上表现为"飞行时长 -6h30m"。解决方法：当相减结果为负数时，加上 1440 分钟（24×60）作为补偿，表示跨越了日期变更线。此方法的前提假设是所有航班的飞行时长不超过 24 小时，对于地球上任意两点之间的直飞航班这是一个合理的假设。但如果系统扩展到包含经停航班或多段联程，飞行时长可能超过 24 小时，届时需要更复杂的日期差计算模型（存储完整的起飞和到达日期时间而非仅时刻字符串）。
问题5：PNR 唯一性的全航线检查
PNR（Passenger Name Record，旅客订票参考号）是 6 位字母+数字的随机码（字符集排除易混淆的 I/O/0/1，实际可用 30 个字符），理论空间为 30^6 ≈ 7.29 亿种组合。_generatePNR() 在生成随机码后调用 _pnrExists() 验证唯一性。最初 _pnrExists() 只检查当前航班的 bookedList（因为当时认为 PNR 只需在单航班内唯一），但 refundByPNR() 的实现需要跨所有航班搜索 PNR（用户只知道 PNR 号不知道航班号），如果两个不同航班上的旅客拥有相同的 PNR，refundByPNR 会退掉第一个匹配到的订单（可能不是用户本意）。解决方法：_pnrExists() 改为遍历全部航班：this.flights.some(f => f.bookedList.searchByPNR(pnr) !== null)。由于本系统数据量小（23 条航线 × 平均 200 个订票 = 约 4600 条记录），这个 O(n×m) 的全扫描在每次生成 PNR 时（订票时调用一次）可以接受。但如果系统规模扩大，需要一个全局的 PNR Set 做 O(1) 查重（见"算法改进设想"第 6 条）。此外，_generatePNR() 使用 do-while 循环确保生成的 PNR 不重复，理论上在最坏情况下（PNR 空间接近耗尽）会陷入无限循环，但对于 30^6 的空间和实际几千条记录的规模，碰撞概率极低（< 0.001%），实践中基本只需 1 次循环。
问题6：多乘客订票的原子性保障
多乘客订票模式允许用户在座位图上为多位旅客分别选座（如张三选 12A，李四选 12C，王五选 15D），然后一次性提交。系统需要对每位旅客分别调用 bookTicket()，每次调用都是独立的交易：扣减 remaining、生成 PNR、分配座位、插入 bookedList 链表。如果在提交第 2 人时失败（例如其选中的座位在两次操作之间被另一个浏览器标签页的操作占用），第 1 人的订票已成事实——remaining 已扣、PNR 已生成、链表已插入——而第 2 人失败——出现"部分成功"的不一致状态。如果只给用户一个笼统的"订票失败"提示，用户不清楚第 1 人是否已经订票成功，可能重复提交导致重复订票。解决方法：实现"预校验 + 批量提交"两阶段模式。预校验阶段：遍历所有乘客表单行，收集姓名、旅客类型、座位号和舱位；校验所有姓名非空且互不重复；检查 remaining >= 乘客总数（整体余票充足）；重新调用 occupiedSeats() 确认所有选中的座位未被在此期间的其他操作占用。只有全部校验通过后才进入执行阶段：逐人调用 bookTicket() 并收集每次的返回结果。如果执行阶段中途仍出现失败（极端情况），将所有成功生成的 PNR 汇总展示并明确标注"部分成功——以下 PNR 已生效"，告知用户哪些人已订票、哪些人未成功，避免信息不对称。这种模式与数据库事务中的"预检查 + 乐观锁"思想类似——假设冲突概率低，先校验再执行，遇到冲突时明确汇报状态而非暗自失败。
问题7：localStorage 序列化与反序列化的数据结构重建
JavaScript 的链表/队列通过对象引用（next 指针）连接节点，JSON.stringify 能序列化对象属性值但无法保留引用关系，且 next 指针会形成嵌套深度等于链表长度的递归结构，在 JSON.stringify 时虽不会报错（因为每次 next 指向的是独立对象而非循环引用），但生成的 JSON 嵌套深度大且冗余。解决方案是双向转换：_persist() 时，每个 Flight 对象调用 bookedList.toArray() 和 waitQueue.toArray() 将链表/队列展平为纯数据数组（每个元素是只含业务字段的普通对象，无 next 指针），然后将整个 flights 数组 JSON.stringify 存入 localStorage 的 airline_v2_data 键。load() 时逆向操作：JSON.parse 得到数组后，逐条创建 Flight 对象，然后对每个航班遍历其 bookedList 数组逐条调用 insert()（重建排序链表），遍历其 waitQueue 数组逐条调用 enqueue()（重建链式队列）。当 CustomerNode 或 WaitNode 增加新字段时（如 v2.0 增加了 passengerType 和 contact），旧版本 localStorage 中存储的数据没有这些字段，反序列化时会得到 undefined。如果不做兼容处理，insert() 的参数位置会错位（undefined 替代了 seatNumbers 数组导致后续操作报错）。解决方式是：load() 中用 try-catch 包裹整个反序列化过程，失败时静默回退到 initTestData()；字段读取时使用默认值兜底（c.passengerType || 'adult'，c.contact || ''）；toArray() 的返回结构需要保持向后兼容（新增字段放在对象末尾，不影响旧字段的数组索引方式读取）。这个问题的教训是：任何涉及持久化的系统，数据格式的版本管理是必需的——理想的方案是在存储数据中加入 version 字段，load 时根据版本号走不同的反序列化路径或迁移逻辑。
问题8：订票时同名检查的范围界定
bookTicket() 在验证阶段调用 f.bookedList.search(name) 检查该姓名是否已在当前航班有订票记录，如果有则拒绝（要求使用其他姓名或先退票）。这个设计简化了退票操作（按姓名退票时唯一确定一条记录），但带来了实际问题：真实场景中可能存在同名不同人（如两个"张伟"都需要订同一航班）。在航司生产系统中，旅客的唯一标识不是姓名而是证件号（身份证/护照号），但本系统作为课程设计未引入证件号字段。当前的折中方案是将同名视为冲突并拒绝，并在提示信息中建议"使用其他姓名"（可加数字后缀如"张伟2"区分）。另一个相关问题是 search(name) 的精确匹配（===）意味着"张伟"和"张 伟"（中间多空格）被视为不同人，可能导致同一人重复订票。简单的防御方法是在输入时做 trim 处理但不能完全解决（用户可能每次输入略有不同），更健壮的方案是实现模糊匹配或引入唯一标识字段。
问题9：cancelFlight() 后候补队列的重建
cancelFlight() 在执行航班取消时，遍历 bookedList 逐人删除（释放座位），同时需要清空候补队列。最初的实现中直接遍历 waitQueue.toArray() 获取快照后，通过多次 dequeue 清空。但如果在 dequeue 循环中直接操作，toArray() 的遍历和 dequeue 的修改可能互相干扰。最终采用更清晰的方案：先获取 waitQueue.toArray() 快照保存为待通知列表，然后直接替换为新 LinkedQueue 实例（f.waitQueue = new LinkedQueue()），旧队列被垃圾回收。类似的，bookedList 的逐人退票也不能在遍历 bookedList 的过程中直接修改 bookedList（遍历指针错乱），而是先获取 toArray() 快照，在快照上迭代，每次对 bookedList 执行 delete 操作。这是"迭代与修改分离"的经典模式——在遍历可变数据结构时，要么先拍快照再修改原结构，要么在遍历过程中收集待删除列表、遍历完成后再批量删除。
三、展示层（app.js）
问题1：座位图从"左驱右"到"右驱左"的交互模式重构
v2.0 的交互模式是"左驱右"：用户在左侧表单选择舱位等级（下拉框）和订票数量 → 系统调用 generateSeatNumbers() 自动在对应舱位分配连续座位 → 座位图被动高亮显示分配结果 → 用户只能接受或更换舱位重试。这种模式的问题是：用户没有选择具体座位的自由（不能选靠窗还是过道、不能选前排还是后排）；自动分配算法可能给出不理想的座位组合（如一家人的座位被分散到不同排）。重构为"右驱左"后：用户直接在座位图上点击任意可用座位（跨舱位自由多选），左侧表单自动跟随变化——订票数量输入框的值自动同步为已选座位数；多选座位时单旅客表单自动切换为多旅客逐座表单；舱位选择下拉框变为参考显示（因为已选座位的实际舱位由座位图决定而非表单决定）。重构的核心技术难点在于维护 State.seatCabinMap 映射对象，它记录了每个已选座位的 seatId 到 cabinClass 的对应关系，后续计价时需要知道每座的实际舱位来计算价格（头等舱座位按头等舱价格、经济舱座位按经济舱价格）。
最初尝试从 DOM 元素的 CSS class 属性反向推断舱位：检查座位元素的 classList 是否包含 'cabin-first'、'cabin-business' 或 'cabin-economy'。但这种方式有两个致命缺陷：第一，class 字符串只是样式标记，不是可靠的数据源——CSS 过渡动画期间 class 可能处于添加/移除的中间状态，且浏览器的 CSS 引擎和 JS 引擎的同步时机不确定；第二，class 名称和 cabinClass 数值之间形成一个隐式约定（cabin-first = 1, cabin-business = 2, cabin-economy = 3），如果后续 CSS 重构改了 class 命名而忘记同步 JS 逻辑，映射会静默失效且没有报错（因为只是 class 对不上，JS 会 fallback 到默认值 3）。最终的可靠方案是在 renderSeatMap() 渲染座位图时同步构建纯 JS 映射：遍历 getSeatMap() 返回的 zones 数组时，每个 zone 有明确的 cabinClass 属性，每渲染一个可用座位（<span class="seat available ...">）就在 State.seatCabinMap[col.id] = zone.cabinClass 记录其舱位。这个映射完全脱离 DOM，不依赖任何 CSS class 字符串，是唯一真实来源（Single Source of Truth）。当用户点击座位选中/取消时，只需要操作 State.selectedSeats 数组的增删和 DOM class 的视觉切换，seatCabinMap 保持不变（座位不会因为被选中而改变舱位类别）。这个问题的本质教训是：DOM 是视图层，不应作为数据层的替代品——任何业务逻辑需要的数据都应该在 JS 内存中有自己的存储（State 对象），"从 DOM 反查数据"是一种脆弱的设计模式。
问题2：多乘客表单的动态渲染与事件绑定时机
当用户在座位图上选择了多个座位后，renderPassengerForms() 会动态生成多位旅客的信息填写表单：单项表单（#single-pax-form）隐藏，多项表单（#multi-pax-form）显示，multi-pax-list 容器内为每个已选座位生成一行输入控件（姓名输入框 + 旅客类型下拉框）。这些 DOM 元素是在运行时动态创建的，而非在 HTML 中预置。这带来了两个事件绑定的挑战。第一，每行的旅客类型下拉框（<select class="pax-type">）的 change 事件需要在旅客切换类型时触发价格重算。由于这些元素是动态生成的，不能直接在 document.querySelectorAll 上一次性绑定（渲染时这些元素还不存在），也不能每次渲染后重新绑定（会有重复绑定累积），因此采用事件委托模式：在父容器 #multi-pax-list 上监听 change 事件，通过 e.target.closest('.pax-type') 判断是否来自目标下拉框。第二，updatePriceDisplay() 在价格重算时需要读取每位旅客的姓名、类型和座位信息。如果 multi-pax-list 的 DOM 行正在渲染中（innerHTML 已设置但浏览器尚未完成布局），querySelectorAll('.passenger-row') 的返回值可能为空或包含不完整的行。因此增加了回退逻辑：当 DOM 行不存在时，直接遍历 State.selectedSeats 数组和 State.seatCabinMap 对象计算价格，绕过 DOM 查询。这形成了一个双重路径设计——正常情况下走 DOM 路径（可读取用户手动选择的旅客类型），DOM 未就绪时走状态路径（使用默认成人类型计算）。
问题3：Toast 通知的堆积与自动清理
用户操作反馈使用 Toast 轻提示组件（固定在页面右上角的半透明消息条）。在快速连续操作场景下——如航班总览页的"取消航班"按钮触发批量退票，连续产生多条通知——Toast 容器可能累积 10 条以上的消息，叠加遮挡页面内容甚至溢出视口。解决方案：在 toast() 函数开头加入容器容量限制——while (container.children.length >= 5) container.firstChild.remove()——确保同时可见的 Toast 不超过 5 条，超出时按 FIFO 顺序移除最早的一条。每条 Toast 通过 setTimeout 在 3 秒后开始淡出动画，再 0.4 秒后从 DOM 中完全移除。两者配合保证了 Toast 消息的"滚动窗口"式展示。此外，Toast 的 CSS 使用 position: fixed 脱离文档流，z-index 设为最高层级，确保不被页面内容遮挡，但同时也需要避免遮挡模态框（确认对话框的 z-index 应高于 Toast）。
问题4：搜索结果排序的状态与视图分离
搜索结果的排序下拉框切换时，sortResults() 从 State.lastSearchResults 浅拷贝一个新数组，按照选定的排序标准（价格升序/降序、起飞时间、飞行时长、余票数）进行排序，然后直接操作 DOM 替换搜索结果容器的内容。这里的关键设计选择是：排序只在视图层进行，不修改 State.lastSearchResults 缓存。如果排序后更新了缓存，那么用户第二次切换排序方式时基于的是已被上一次排序改变顺序的数据，导致"按价格排序后再按时间排序"的结果变成"按时间排序"（上一次排序的效果被覆盖）而非"在原始搜索结果上按时间排序"。保留原始搜索结果的顺序不变，每次排序时基于相同的原始数据重新排序，保证了不同排序方式之间的独立性。这个问题的教训是：缓存数据和展示数据应该是两个不同的层——缓存保持"源数据"不变，展示数据可以根据 UI 需求随时重新排列/过滤而无需回写缓存。这也符合单向数据流的原则。
问题5：航班取消后的多视图 UI 一致性
当用户在某处（航班总览页的"取消航班"按钮或订票页）取消了航班后，Flight 对象的 canceled 属性设为 true、remaining 归零。但系统中有多个视图引用了该航班：总览表需要显示"已取消"徽标并禁用操作按钮；订票页面的航班下拉列表需要禁用已取消航班；退票和候补查询的下拉列表同样需要排除或标记已取消航班。最初只有总览表的渲染逻辑检查了 canceled 属性并显示徽标，但 populateFlightSelects() 和 populateManageSelects() 在下拉列表生成时未过滤已取消航班，导致用户可以在订票下拉中选中已取消的航班，触发 onSelectFlight() 后能正常渲染座位图（因为 Flight 对象本身还在内存中且数据结构未变），但在最终 doBook() 时会遇到逻辑矛盾（canceled 航班是否应该允许订票？bookTicket 中没有检查 canceled 标记）。解决方法是：在所有下拉列表的生成函数中，为已取消航班添加 disabled 属性和取消标识文字（如 "CA1001 — 北京→上海 ❌已取消"），在 UI 层面阻止用户选择；同时统一各视图的渲染逻辑，确保已取消航班的展示一致（总览表显示徽标、展开行中显示订票名单但标记为已退票状态）。这是一个典型的"状态变更需要通知所有视图"问题——在小型纯前端项目中通过手动调用 refreshAll() 来统一刷新所有视图即可满足，但在大型项目中需要引入发布-订阅模式或状态管理库实现自动同步。
问题6：自定义确认对话框的清理与事件泄漏
showConfirm() 和 showAlert() 函数通过动态创建 DOM 元素（.confirm-overlay）来替代浏览器原生 confirm/alert 对话框。每次调用都会在 document.body 上追加一个新的 overlay 元素。如果在旧对话框尚未关闭时再次调用（例如用户在短时间内连续点击退票按钮），代码虽然通过 if (old) old.remove() 移除了旧的 overlay，但旧 overlay 上绑定的 keydown 事件监听器（用于 ESC 关闭）并未随 DOM 移除而自动解绑——因为在 addEventListener 时监听器被添加到 document 而非 overlay 元素上。如果反复弹出关闭对话框，document 上会累积多个 keydown 事件处理器，每次按 ESC 都会触发所有累积的处理器。解决方式有两种：一是将 keydown 监听器绑定在 overlay 元素自身（而非 document），overlay 被 remove 时监听器随元素销毁；二是在移除旧 overlay 时显式调用 removeEventListener。当前代码采用第一种思路的变体——将监听器函数存储在局部变量 escHandler 中，并在回调中通过 removeEventListener 自清理，但需确保每次创建新对话框前旧对话框的监听器已被清理。这个问题的教训是：手动管理 DOM 事件生命周期必须考虑"创建时绑定、销毁时解绑"的配对原则，否则会造成事件泄漏和意外的多重触发。
问题7：Tab 切换时滑动指示器的位置计算
Tab 导航栏下方有一个滑动指示器（通过 CSS custom properties --tab-left 和 --tab-width 控制位置和宽度），在切换 Tab 时通过 updateTabIndicator() 更新。该函数通过 getBoundingClientRect() 获取当前激活按钮的位置和宽度，计算相对于导航栏的偏移量，然后设置 CSS 变量触发过渡动画。调试时发现两个问题：第一，在页面首次加载时 Tab 按钮的布局可能尚未完成（CSS 字体加载中），getBoundingClientRect() 返回的值为 0，导致指示器不可见；解决方式是使用 setTimeout(updateTabIndicator, 100) 延迟到首帧渲染完成后执行，并在 window resize 时重新计算。第二，在 switchTab() 中如果先移除所有 active class 再添加新 active class，会导致一个短暂的"无激活按钮"状态，指示器的 getBoundingClientRect() 查询不到激活按钮而报错；解决方式是确保在查询前已设置好新的 active class（先添加 class 再调用 updateTabIndicator）。
四、样式层（style.css）
问题1：座位图液态玻璃效果在 Safari 中的渲染差异
座位图的机身 (.fuselage) 使用 backdrop-filter: blur(10px) 配合半透明背景 background: rgba(255,255,255,0.08) 实现磨砂玻璃（Glassmorphism）视觉效果——机身区域后面的内容会呈现模糊的透光感。在 Chrome/Firefox 中表现正常，但在 Safari（特别是 iOS Safari 和 macOS Safari 15 以下版本）中存在两个兼容性问题：一是 backdrop-filter 需要 -webkit-backdrop-filter 私有前缀，不加前缀时属性被忽略，退化为不透明背景；二是在某些 Safari 版本中，backdrop-filter 与 border-radius 组合时，模糊效果不受圆角裁剪，会溢出到机身外框的直角区域，破坏了液态玻璃机身的美观性。解决方法：同时声明 backdrop-filter 和 -webkit-backdrop-filter 两个属性；在 .fuselage 容器上叠加 overflow: hidden 强制裁剪圆角外的溢出内容；使用 transform: translateZ(0) 或 will-change: transform 创建独立的 GPU 合成层，这可以解决部分 Safari 版本的渲染层级问题。此外，backdrop-filter 在性能较差的设备上（低端 Android 设备）可能导致滚动卡顿，这在响应式设计（移动端访问）时需要考量——可以通过媒体查询在移动端降级为纯色半透明背景。
问题2：座位 hover 弹起动画的 z-index 层叠冲突
座位 (.seat) 在 hover 状态通过 transform: translateY(-3px) scale(1.08) 和 box-shadow 的增强实现"弹起+放大"的视觉反馈。但由于 DOM 元素按文档流顺序渲染，后渲染的元素（右侧座位/后排座位）默认覆盖在前渲染元素（左侧座位/前排座位）之上。当用户 hover 一个座位时，该座位虽然在 Y 轴方向"弹起"，但在 Z 轴方向（层叠顺序）仍然被相邻的后续兄弟元素遮挡——hover 的阴影被相邻座位元素截断，弹起效果大打折扣。解决方法：在 .seat:hover 伪类中添加 position: relative; z-index: 2，利用 relative 定位触发 z-index 生效（默认 static 定位的元素 z-index 无效），使得当前 hover 的座位在 Z 轴上高于所有相邻座位。这个问题的本质是 CSS 层叠上下文（Stacking Context）的理解：z-index 只在定位元素（position 不为 static）上生效，且只在同一层叠上下文中比较。如果 .seat-row 上设置了 transform 创建了新的层叠上下文（本系统中未设置），则子元素的 z-index 只在 row 内部有效，无法跨行比较。
问题3：响应式布局下的座位图缩放
座位图设计为桌面端优先（机身宽度约 600px），在移动端（屏幕宽度 < 480px）会出现横向溢出。由于座位图中包含固定宽度的列布局（每排 3-3 或 2-2 布局 + 过道间距），简单的 width: 100% 缩放会导致座位元素过小而无法点击。解决方式：在移动端媒体查询中，将 fuselage 容器设置 overflow-x: auto 允许横向滚动（而非强制缩放），同时减小座位元素的尺寸（从 40px 降至 32px）、间距和字体大小，保持可点击区域不小于 28×28px（符合移动端触摸目标的最小推荐尺寸）。另外，座位图上的 tooltip（.seat-tip）在移动端无法通过 hover 触发（触摸屏无 hover 状态），改为在座位被选中时显示简化的 tooltip 信息。这个问题的思考：响应式设计不仅仅是"缩放"，而是针对不同交互模式（鼠标精确点击 vs 手指模糊触摸）和屏幕尺寸重新思考布局和信息密度。
算法改进设想
1. 已订票排序链表的查找优化——增加哈希索引
当前 SortedLinkedList 的 search(name) 和 searchByPNR(pnr) 都是 O(n) 的链表遍历，从 head 开始逐节点比对直到找到匹配或到达链表末尾。对于本系统（单航班订票人数通常 < 300 人），这个开销可以接受。但链表的本质优势在于插入和删除（O(1) 在已知位置时），而非查找。改进方案：在 SortedLinkedList 内部维护一个辅助 Map，key 为 name，value 为对应的 CustomerNode 引用，同时在 searchByPNR 上也维护一个反向 Map（key 为 pnr）。每次 insert 时向两个 Map 添加条目，每次 delete 时从两个 Map 删除条目。这样 search 和 searchByPNR 都降至 O(1)。代价是 insert 操作从纯 O(n)（遍历找位置 + O(1) 指针操作）变为 O(n)（遍历找位置）+ O(1)（Map 插入），总体复杂度不变但常数因子增加；内存占用因两个 Map 的额外存储（每个节点多 2 个 Map 条目）增加约 50%。在内存充裕的浏览器环境下，用空间换时间是合理的。此外，Map 的存在可以完全替代链表遍历查找，使得 SortedLinkedList 退化为仅维护排序顺序（用于 toArray 按姓名排序输出）的结构，而查找功能完全由 Map 承担。这是典型的"索引加速"模式——主数据结构保持不变以满足核心约束（按姓名排序的链表），辅助索引提供快速访问路径。
2. 航班搜索的多维倒排索引
当前 AirlineSystem.searchFlights() 对 this.flights 数组做完全顺序扫描（O(n)），每条航线逐一检查始发站、终点站、日期、时段、价格、机型等过滤条件。对于 23 条航线的测试数据，顺序扫描在亚毫秒级完成。但如果航线数量增长到真实航司水平（如每天数千条航线），顺序扫描的延迟会线性增长。改进方案：在 AirlineSystem 中维护三个倒排索引（均为 Map 结构）——originIndex: Map<城市名, Flight[]>，按始发站映射；destIndex: Map<城市名, Flight[]>，按终点站映射；dateIndex: Map<日期字符串, Flight[]>，按飞行日期映射。在 addFlight() 时向三个索引添加条目，在 cancelFlight()（或删除航班）时移除。搜索时，根据用户输入的始发站和终点站分别查询对应索引得到两个 Flight[] 候选集，取交集；如果指定了日期，再与日期索引的候选集取交集。对缩小后的候选集应用价格/时段/机型等精细过滤和排序。三个索引的维护是增量的（每次 addFlight 做 3 次 Map.set），不增加搜索时的扫描开销。但需要注意：当 Flight 对象的属性变更（如取消航班改变了状态）时，不需要从倒排索引中移除（因为 canceled 是过滤条件而非索引键），只需在精细过滤阶段检查即可。倒排索引的代价是增加了内存占用（每个 Flight 对象在 3 个 Map 中有引用，引用本身很小）和 addFlight 的复杂度（从 O(n) 排序插入变为 O(n) + O(1) 索引更新）。
3. occupiedSeats() 的增量维护
当前 occupiedSeats() 在每次被调用时都执行完整的 bookedList.toArray() 遍历（O(n)）+ Set 构建（O(m)，m 为已订票旅客数）。改进方案：在 Flight 类中维护一个 _occupiedSeatsCache 属性（Set 类型，初始为空），在 bookTicket() 成功时为每位旅客的 seatNumbers 数组中的每个座位执行 cache.add(seatId)；在退票时执行 cache.delete(seatId) 对每个释放的座位；在 cancelFlight() 时直接 cache.clear()。occupiedSeats() 变为直接返回 _occupiedSeatsCache（或返回 new Set(_occupiedSeatsCache) 做浅拷贝以防止外部修改）。从 O(n) 到 O(1) 的性能提升在频繁调用场景中非常显著——座位图渲染（每个座位的 occupied 属性查询）从全表扫描变为 Set.has 的 O(1) 检查。代价是：需要在所有修改已占用座位的代码路径上同步更新缓存，遗漏任何一处就会导致缓存与链表数据不一致，而这种不一致是静默的（不会报错，但座位图显示错误）。防范措施是将缓存更新逻辑封装在私有方法中（如 _occupySeats(seatNumbers) 和 _releaseSeats(seatNumbers)），所有公开方法通过调用这些私有方法来间接修改缓存，减少遗漏的可能。
4. generateSeatNumbers() 的预计算优化
当前座位分配采用"按需遍历"方式——每次调用 generateSeatNumbers() 时实时遍历行列网格，跳过已占用座位，收集满足数量的空座。改进方案：在 Flight 构造时或每次座位占用变更后，预计算并缓存三个舱位的可用座位列表（firstAvailable, businessAvailable, economyAvailable），每个列表是座位号数组，按排号升序排列。分配座位时，先从目标舱位的可用列表中取前 count 个，不足时从全局可用列表（三舱列表合并）中取剩余数量。预计算在订票和退票时增量更新：订票时从对应舱位的可用列表中移除已分配的座位号；退票时将释放的座位号按舱位重新插入对应列表并保持排序。这样 generateSeatNumbers() 从 O(n) 的行列遍历降为 O(k)（k = 需求座位数，直接取数组前 k 个元素）。代价是：需要维护三个附加的数组（每个座位号占约 5 字节，300 座 × 5 字节 × 3 ≈ 4.5KB，可忽略）；插入和删除可用座位时需要保持数组有序（可使用 splice 配合二分查找，O(log n) 查找 + O(n) 移动，但在 100 以下的数组规模中线性插入也足够）。
5. 候补队列的批量匹配与部分满足策略
当前的 _fulfillWaitlist() 采用"全有或全无"的单队头检查策略。改进设想是支持"部分满足"——当队头需求大于余票时，不完全放弃，而是分配剩余的全部票给队头（部分满足），队头的剩余需求可以选择保留在队头继续等待或降级为更小的候补记录。例如，队头需要 3 张票，释放了 2 张，可以先分配 2 张给队头，队头剩余 1 张需求继续留在队头等待。真实航司系统的候补更接近这个模型——乘客通常会接受"有几张给几张"。但实现部分满足引入了几个新问题：首先，已部分满足的候补者已经获得了 PNR 和座位号，不再是"无票"状态，但其另一部分需求仍在队列中，候补队列的节点需要增加"已满足数量"和"关联 PNR"字段来追踪这种中间状态；其次，部分满足打破了"一人一 PNR"的简单映射，同一旅客可能持有多个 PNR（每次部分满足生成一个新 PNR），给退票管理带来复杂性；第三，候补队列的"位置"概念变得模糊——一个部分满足的候补者仍然在队头位置吗？如果移出队头，后续新退票释放的余票如何分配？这些复杂性是本系统作为课程设计暂未引入部分满足策略的原因。
6. PNR 全局唯一性检查的哈希加速
当前 _pnrExists() 遍历全部航班的全部订票记录（最坏 O(F × P)，F 为航班数，P 为每航班平均订票人数）。改进方案：在 AirlineSystem 中维护一个 _pnrSet（Set 类型），在每次生成 PNR 并成功订票后 add(pnr)，在退票时根据业务需要可以选择保留（退票的 PNR 不应该被重用，以保持历史记录的可追溯性）或 delete（释放 PNR 供重用）。_pnrExists() 变为 _pnrSet.has(pnr)（O(1)）。在 load() 反序列化时需要重建 _pnrSet：遍历所有航班的所有订票记录将所有 PNR 加入 Set。这个优化在 PNR 生成的高频调用场景（批量订票）中效果显著，将 O(F×P) 的全表扫描变为 O(1) 的哈希查找。
7. localStorage 持久化的增量序列化
当前 _persist() 将整个 this.flights 数组（包含所有航班的所有订票和候补数据）完整序列化为 JSON 写入 localStorage——相当于每次都做"全量快照"备份。改进方案：实现"脏标记"（Dirty Flag）模式。每个 Flight 对象增加 _dirty 布尔属性，在其状态变更时（bookTicket、refundTicket、cancelFlight、enqueue、dequeue 等）设为 true。_persist() 检查所有航班的 _dirty 标记，只序列化脏航班，与 localStorage 中已有的非脏航班数据合并后写入。或者更进一步：localStorage 中维护每个航班独立的键（如 airline_v2_flight_CA1001），每次只更新变更航班的键，完全避免全量序列化。对于当前 23 条航线、每次序列化 < 50KB JSON 的规模，全量 IO 在 localStorage（同步 API）上的耗时在 1-5ms 范围，不是瓶颈。但增量序列化的价值在于降低不必要的写入——localStorage 的写入是同步的、会阻塞主线程，频繁写入（如每次订票都触发 _persist）会导致 UI 卡顿。脏标记模式下，可以配合防抖（debounce）策略：_persist 在操作完成后 500ms 延迟执行，期间多次操作只触发一次持久化，减少 IO 频率。
8. 航班有序插入的二分查找定位
当前 addFlight() 使用 flights.findIndex(x => x.flightNo.localeCompare(flightNo) > 0) 做线性扫描定位插入位置，配合 splice(pos, 0, flight) 插入。查找是 O(n)，插入（splice 导致的元素后移）也是 O(n)。改进方案：查找部分使用二分搜索——由于 flights 数组已按航班号升序排列（这是由 addFlight 的有序插入保证的不变量），可以在 O(log n) 时间内找到正确的插入位置。但 splice 的元素移动仍然是 O(n)，这是 JavaScript 数组的底层特性决定的（数组在内存中连续存储，中间插入需要移动后续所有元素）。对于 23 条航线的规模，二分 vs 线性在绝对时间上没有可感知的差异（都是亚毫秒级），但作为算法意识的体现——面对"已排序的顺序表"时，查找操作选择 O(log n) 的二分而非 O(n) 的线性是正确的工程习惯。如果航线数量增长到数千条，二分的优势才会显现。值得注意的是，JavaScript 没有内置的二分查找方法，需要手动实现 while (lo < hi) 循环，且需注意边界条件（插入位置是第一个大于新航班号的索引，二分查找的 mid 计算和 lo/hi 更新需要与此语义匹配）。
9. 座位图渲染的虚拟化
当前 renderSeatMap() 一次性将整个飞机的所有排、所有座位渲染为 DOM 元素——300 座的飞机 = 50 排 × 6 列 = 约 300 个 .seat 元素 + 装饰元素（过道、排号、舱位标题、机尾标识），总计约 400 个 DOM 节点。浏览器的布局和绘制引擎在 500 节点以下表现流畅。改进设想：对于未来可能支持的超大型飞机（A380 双层约 500-800 座、或系统扩展为同时展示多架飞机），可采用虚拟滚动技术——只渲染当前视口内可见的排（如 8-10 排 = 约 60 个座位），上下滚动时动态替换视口外的 DOM（回收并复用）。这需要引入一个滚动容器，计算每排的高度，根据 scrollTop 确定可见排的范围，动态生成可见排的 DOM 结构。虚拟滚动的实现复杂度较高（需要精确计算行高、处理滚动条的跳变、保持座位选中状态在虚拟替换中的连续性），对于当前系统的规模属于过度工程，但作为前端性能优化的前沿方向值得了解。
10. 旅客类型折扣的查表优化
当前 passengerType 的折扣乘数在代码中多处硬编码：bookTicket() 中有一个 { adult: 1.0, child: 0.75, infant: 0.1 } 的字面量；lookupByPNR() 中同样的映射被重复定义；UI 层的 updatePriceDisplay() 中也再次硬编码。如果未来增加新的旅客类型（如学生票、老年票、军人票），需要在 3-4 处同步修改。改进方案：将旅客类型与折扣乘数的映射抽取为全局常量（如 PASSENGER_TYPE_MULTIPLIER = { adult: 1.0, child: 0.75, infant: 0.1 }），所有需要查询折扣的地方引用此常量。更进一步，可以在 Flight 或 AirlineSystem 层面支持自定义折扣策略（如特定航班对儿童票有额外优惠），将折扣乘数与航班对象关联而非全局统一。这不仅是代码质量改进（DRY 原则），也是业务扩展性的支撑。
